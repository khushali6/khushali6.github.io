Agentic coding system

Your coding environment, from your pocket.

Describe what you want. Meadow plans it, builds it phase by phase with a real coding engine, tests every step, and reports back on Telegram.

Open source · beta · MITDesigned and built end to end

Overview

Meadow runs on your own computer. You send a request from a dashboard or Telegram — text, voice or a PLAN.md — approve the plan, and Meadow drives a coding engine (the Cursor CLI is the most tested; Codex CLI, Gemini CLI or any command-line tool also work) until every phase passes its checks. Code, memory and keys stay on your machine.

The interesting part isn't that an LLM writes code. It's what happens when the code it writes is wrong.

I wanted to work on the part around the model: the harness that decides what it may touch, checks what it produced, and puts a human back in the loop. A single long agent session drifts, mixes unrelated changes and leaves little evidence — so Meadow breaks the work into phases that can each fail on their own.

How it works

  • Request. Meadow classifies it (new app, feature, bug, question) and asks up to five short questions.
  • Spec and plan. It writes SPEC.md and a phased PLAN.md. Every phase has at least one check that can actually fail.
  • Approval. Nothing touches code until you approve — on the dashboard or with one tap on Telegram.
  • Build. Each phase runs on its own branch; guards inspect the diff, checks run, and failures go back to the engine with the real error, up to three attempts.
  • Merge. Only passing work is committed and fast-forwarded onto main, with a summary, diff stats and screenshots.
  • Browser tests. For web apps, Meadow starts the app, clicks through each main user flow in a headless browser and sends desktop and mobile screenshots.

Request → spec → plan

Text, voice or a PLAN.md becomes a specification and a phased plan. Phases are the unit of work, approval and rollback.

# PLAN.md
1. scaffold & schema
2. api routes
3. auth flow
4. dashboard ui

Supervisor

A supervisor model (Ollama, FreeLLMAPI or Claude) reviews failures, reports progress over Telegram, and lets independent phases run in parallel.

Coding engine

The engine does all the editing, headless, one phase at a time. The agent model only plans and summarises.

Tools / MCP

Every tool has a risk level. Writes and risky commands wait for approval, every call lands in an audit log, and secrets never appear in prompts, logs or the UI.

tool fs.write src/auth/session.ts
gate approval required: shell.exec
audit recorded

Git branch

Each phase runs on meadow/phase-<id>-<slug>, so work is isolated, reviewable and reversible.

Checks + tests

Checks (cmd, file_exists, http) decide whether a phase may merge.

✗ expected 401, got 200
→ real error returned to the engine (attempt 2/3)

CodeAtlas

A local knowledge graph of services, APIs, tables, releases and incidents, so Meadow can answer “why did payments start failing after v2.4?” with cited evidence.

What I built

  • The harness: branch-per-phase execution, guard checks, test runs and the retry loop.
  • The supervisor agent, Telegram control surface and parallel execution of independent phases.
  • Tool calling and MCP integration with approval gates and audit logs.
  • CodeAtlas, the local knowledge graph, plus a search index and notes per project.
  • Headless-browser flow tests with desktop and mobile screenshots.
  • A cross-platform setup script (startup.sh / startup.ps1) and a meadow doctor command.

The interesting decisions

Why does every phase get its own git branch?

So each phase is independently checkable and reversible. A failing phase can't contaminate the rest, and merging becomes a decision made on evidence rather than a side-effect of the agent finishing.

Why send the real error back instead of “try again”?

A retry without information repeats the same mistake. The actual failing output gives the engine something concrete to fix — which is what a developer would do.

Why approval gates and audit logs?

Give agents tools, not superpowers. The agent acts through explicit, inspectable tools, a human can veto risky actions, and there's a record of what happened.

Why local-first?

Code, memory and keys stay on your machine, and Meadow never signs in for you or reads .env files.

Where it breaks

A phase keeps failing. After three attempts it stops and tells you why. You can retry with a hint, skip, or roll back — it never merges.
The checks are weak. Meadow verifies what the checks measure, so a weak check proves little. That's why plans must include checks that can fail.
Beyond localhost. Browser screenshots work for web apps on localhost only.

Results

Meadow is open source (MIT) and in beta. CI tests every commit on macOS, Linux and Windows with Node 22.16, 24 and 26. I haven't published success-rate benchmarks yet, so there are no made-up numbers here.

What I'd build next

  • An evaluation suite: success rate and retries across a fixed set of tasks.
  • Smarter supervisor policies for when to stop retrying and escalate.
  • Claude Code as a first-class engine (it's listed as coming soon).
